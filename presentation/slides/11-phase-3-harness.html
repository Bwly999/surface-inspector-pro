Harness Engineering
深度交互百科

什么是 Harness Engineering?

围绕 AI Agent 设计和构建约束机制、反馈回路、工作流控制和持续改进循环的系统工程实践。解决 Agent 在强大生成能力背后的可靠性、一致性与可维护性问题。

核心类比： 马具 (Harness)。LLM 是蛮力十足的“马”，Harness 是将其力量引向正确方向的“缰绳与鞍具”。
  • CPU 与 OS： 模型是 CPU，Harness 是操作系统。CPU 再强，OS 拉胯也白搭。
  • 纠错即设计： 每当发现 Agent 犯错，就设计一个环境级解决方案，确保不再重犯。

为什么需要 Harness?

模型能力不是瓶颈： 实验证明，仅改变 Harness 的工具格式，Grok Accuracy 从 6.7% 跃升至 68.3%。

Agent 的典型失败模式：

  • One-shotting： 试图一步到位导致上下文耗尽，留下半成品。
  • 过早宣布胜利： 看到部分进展即认为任务完成。
  • Dumb Zone 陷阱： 上下文占用超过 40% 后，模型开始产生幻觉、循环和错误调用。

Harness 四大支柱

  • 上下文架构 (Context Arch)： 渐进式披露，分层上下文。区分热记忆、领域专家与冷记忆库。
  • Agent 专业化 (Specialization)： 角色拆解 (Research, Plan, Execute, Review)。19 个领域专家 Agent。
  • 持久化记忆 (Persistent Mem)： 进度检入文件系统。通过 AGENTS.md 建立活的反馈回路。
  • 结构化执行 (Structured Exec)： 思考与执行分离。理解 → 规划 → 执行 → 验证。审查计划比审查代码快。

核心组件详解

  • AGENTS.md： Agent 的 README。文档即反馈循环，不仅仅是静态制品。
  • 机械化约束 (Mechanical Const)： Linter 报错即修复指令。如果无法机械化执行，Agent 必会偏离。
  • 可观测性集成： 浏览器自动化 (Puppeteer)、DOM 快照、遥测驱动的 Bug 修复。
  • 垃圾回收 (GC)： 熵管理 Agent。定期清理冗余代码与文档不一致，对抗熵增。

工程师角色的转变

从“写代码”到“设计环境”： 核心工作是诊断 Agent 缺少什么才能可靠工作，焦点从实现转向赋能。
  • 规划即编码： 在审查计划之前不允许写代码。初始化 Agent 生成 200+ 功能列表并追踪状态。
  • Agent 队长： 负责思考 Agent 如何融入团队工作流，管理清理吞吐量与生成吞吐量。

业界六大共识

  • 共识 1： 瓶颈在基础设施，不在模型智能。
  • 共识 2： 文档必须是活的反馈回路，不是静态制品。
  • 共识 3： 思考与执行必须分离 (先规划再执行)。
  • 共识 4： 上下文不是越多越好 (40% Smart Zone)。
  • 共识 5： 约束必须机械化执行，不能靠文档记录。
  • 共识 6： 角色转型：Relocating Rigor (严谨性从代码转移到系统)。
